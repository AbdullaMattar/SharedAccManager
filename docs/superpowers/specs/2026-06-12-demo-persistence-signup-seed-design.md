# Demo Persistence, Sign-up & Realistic Seed — Design

**Date:** 2026-06-12
**Status:** Approved by user (conversation, 2026-06-12)

## Goals

The Azure demo (`shared-acc-app` on Azure Container Apps, France Central) currently loses all data on every update and every scale-to-zero idle restart, the demo-login button fills credentials that don't match the deployed admin, there is no way for a visitor to create their own account, and the seed data is too thin to look like a real business.

1. **Persist data** across updates and restarts using Azure Files (~$1/month) — no paid database.
2. **Align demo credentials**: deployed admin = `admin@example.com` / `admin123`, matching the existing «استخدم حساب تجريبي» button.
3. **Public sign-up**: visitors can create their own (staff-role) account from the login page.
4. **Realistic seed**: a fresh database boots with enough Arabic-language demo data that the dashboard, expiring page, and revenue charts look like a real subscription-selling business.

Non-goals: multi-tenancy, email verification, password reset for self-registered users, PostgreSQL migration, multiple replicas.

## Feature A: Azure Files persistence

**Storage:** one Storage Account + one Azure Files share, mounted at `/app/data` in the container app. SQLite file lives on the share; the container becomes fully disposable.

**Code change (`lib/db/src/index.ts`):** SQLite WAL journal mode does not work on SMB network shares (requires shared-memory files). Add:
- `SQLITE_JOURNAL_MODE` env var — allowlist `wal | delete | truncate`, default `wal` (local/dev behavior unchanged). Azure deployment sets `delete`.
- `busy_timeout = 5000` pragma — mitigates SMB lock latency.

**Deploy change (`deploy.sh`):**
- Create storage account (globally-unique name, stored/reused like secrets) + file share `appdata`.
- Register the share with the Container Apps environment (`az containerapp env storage set`, ReadWrite).
- Mount it: `az containerapp show -o json` → small Node script adds `template.volumes` + `containers[0].volumeMounts` → `az containerapp update --yaml <file>` (JSON is valid YAML).
- Set `SQLITE_JOURNAL_MODE=delete` env var.
- Default `ADMIN_PASSWORD` changes `changeme` → `admin123`.

**Constraint:** single replica only (already true: `max-replicas 1`). SQLite on SMB must not be accessed concurrently from multiple replicas.

## Feature B: Public sign-up

**API pipeline:** endpoints are defined in `lib/api-spec/openapi.yaml` and code-generated by orval into `@workspace/api-zod` (zod schemas) and `@workspace/api-client-react` (react-query hooks). Register follows that pipeline — no hand-written client code.

**Spec:** `POST /auth/register`, operationId `register`, request `RegisterInput { name: string (min 1), email: email, password: string (min 8) }`, responses `200 AuthUser`, `400/409 ErrorResponse`.

**Server (`artifacts/api-server/src/routes/auth.ts`):**
- Validate with generated `RegisterBody`.
- Role hardcoded `staff`; `bcrypt.hashSync(password, 12)`.
- Duplicate email → 409 «البريد الإلكتروني مستخدم بالفعل» (same pattern as admin user-create).
- On success: insert audit-log entry (`user_register`), call `setSession` (auto-login), return AuthUser shape.
- Rate limit: new limiter on `/api/auth/register` in `app.ts` (10 requests / 15 min), same style as `loginLimiter`.

**Frontend (`artifacts/accounts-manager/src/pages/login.tsx`):**
- Mode toggle on the existing card: «إنشاء حساب جديد» link switches to a registration form (name, email, password, confirm-password with client-side match check); «لديك حساب؟ سجّل الدخول» switches back.
- Uses generated `useRegister` hook; on success, same query-cache flow as login (auto-redirect to dashboard).
- New strings added to `strings.auth` in `src/lib/strings.ts` (all Arabic).

## Feature C: Realistic seed (`artifacts/api-server/src/seed.ts`)

Rewritten with handwritten deterministic data arrays (no new dependencies). Same guards as today: admin user created if missing; demo data only inserted when `products` table is empty — so a persistent database is seeded exactly once.

All dates are computed **relative to the current date** so the demo always looks fresh:

- **Users (2):** admin `admin@example.com` / `$ADMIN_PASSWORD` (default `admin123`); staff demo user `staff@example.com` / `staff123` («موظف تجريبي»).
- **Products (6):** Netflix, Spotify, Shahid VIP, ChatGPT Plus, Disney+, YouTube Premium — Arabic names, realistic capacities (1–6), durations (30 days), prices ($4–25).
- **Accounts (~10):** spread across products, encrypted passwords via existing `encrypt()`, slots auto-created per capacity; statuses: mostly `active`, one `needs_attention`, one expiring within days.
- **Customers (20):** Arabic names, unique Jordanian-style phone numbers (`07XXXXXXXX`), some with WhatsApp/email/notes.
- **Subscriptions (~30):** ~18 `active` (expiries spread 3–45 days out; at least 5 within 7 days so the expiring page shows alerts), ~8 `expired`, ~4 `cancelled`. Each occupies a distinct slot (respects the one-active-per-slot unique index — expired/cancelled subs may share slots with active ones). Slot statuses updated to `occupied` for active subs.
- **Payments (~40):** 1–2 per subscription, `paidAt` spread over the past 6 months, mix of `cash`/`transfer`, amounts matching subscription prices — gives the revenue charts a visible trend.

## Rollout order

1. Code changes (A-code, B, C) → typecheck → commit → push → CI builds image tagged with new SHA.
2. `deploy.sh` updated (A-deploy) → run it: creates storage, mounts share, deploys new image.
3. Fresh share = empty DB → migrations + rich seed run once → data persists thereafter.
4. Verify: login via demo button works; register a new account; data survives `bash deploy.sh` re-run.

## Testing

No test framework exists in the repo; verification is `pnpm run typecheck` (all packages) plus the manual smoke flow in step 4. The seed module stays import-free of app state (pure data + db calls) so a test harness can be added later.
